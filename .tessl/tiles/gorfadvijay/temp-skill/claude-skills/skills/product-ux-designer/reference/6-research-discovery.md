# UX Research and Discovery

> Structured process for turning raw user data into actionable product insights.
> Use when starting a new product, feature, or redesign. Also useful when you need to understand WHO uses a page before designing it.

## Input

Any combination of:
- User interview transcripts or notes
- Support tickets or customer feedback
- Survey responses
- Product analytics or usage data
- Competitor user reviews
- Product context and domain knowledge
- The user's general ideas about who the audience is

---

## Phase 1: Synthesize Raw Data

For each data source:
1. Extract direct quotes revealing goals, frustrations, or behaviors
2. Tag each: speaker, context, emotional intensity (neutral/frustrated/delighted)
3. Identify stated vs revealed preferences (what users SAY vs DO)
4. Flag contradictions between users

**Clustering rules:**
- Group by behavior patterns, not demographics
- A theme needs evidence from ≥2 sources to be valid
- Outliers noted but not elevated unless strategically important

---

## Phase 2: Map Jobs to Be Done

For each identified job:

```
When [situation/trigger],
I want to [motivation/desired progress],
So I can [expected outcome].
```

Classify each job:
- **Core functional** — the main task
- **Related** — done before/after/alongside
- **Emotional** — how they want to feel
- **Social** — how they want to be perceived

Identify:
- Current solutions (including workarounds and manual processes)
- Switching triggers — what would make them adopt something new?
- Hiring criteria — what they evaluate when choosing a tool

---

## Phase 3: Evidence-Based Personas

For each behavioral segment:

| Field | Content |
|-------|---------|
| **Name + Archetype** | Descriptive, not demographic: "The Power User" not "Sarah, 32" |
| **Primary goal** | One sentence |
| **Context of use** | When, where, how often, what device |
| **Key behaviors** | What they actually DO (not say) |
| **Frustrations** | Specific, evidence-backed |
| **Current workarounds** | What they do today |
| **Decision criteria** | What matters when choosing |
| **JTBD alignment** | Which jobs map to this persona |

**Rules:**
- Never include demographics unless they directly affect behavior
- Every attribute links to evidence
- Can't distinguish two personas by behavior? Merge them.
- Max 3-4 personas (more = useless)

---

## Phase 4: Pain Point Analysis

For each pain point:

| Property | Content |
|----------|---------|
| Description | What's the problem? |
| Frequency | Daily / Weekly / Rarely |
| Severity | Annoyance / Blocker / Deal-breaker |
| Current workaround | What do users do today? |
| Evidence | Quotes or observed behaviors |
| Priority | Frequency × Severity |

---

## Phase 5: Opportunity Mapping

For each opportunity:

| Property | Content |
|----------|---------|
| Statement | [User type] needs a way to [need] because [insight] |
| Size | All / Most / Some / Few users affected |
| Impact | High / Medium / Low value if solved |
| Feasibility | Easy / Moderate / Hard |
| Priority | Size × Impact ÷ Feasibility |
| JTBD connection | Which job this serves |
| Competitive gap | How well competitors solve this |

---

## Output Format

### 1. Research Summary (1 paragraph)
What we learned, biggest surprise, most important insight.

### 2. Key Themes (3-5)
Ranked by strength of evidence.

### 3. Jobs to Be Done
Complete JTBD statements with classification.

### 4. Personas (2-4)
Evidence-based behavioral personas.

### 5. Pain Points
Ranked table with frequency, severity, priority.

### 6. Opportunity Map
Ranked opportunities with sizing and feasibility.

### 7. Notable Quotes
5-10 most revealing direct quotes with context.

### 8. Open Questions
What we still don't know and how to find out.

---

## Quality Bar

- Every insight traces to specific evidence
- Never fabricate user behavior
- Distinguish "users said" vs "users did"
- Personas distinguishable by behavior, not demographics
- Opportunities actionable — a team can start working on them
- Gaps acknowledged explicitly
